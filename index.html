    Source: Patchstack via The Next Web

  3. Official PoC Exploit Published

    September 23, 2026

    Security researcher Robert Ressl, who originally discovered and responsibly disclosed the vulnerability to WordPress, published the official Proof-of-Concept (PoC) exploit along with a reproducible lab environment. The PoC demonstrated how manipulating the page slug allows the template loader to reach readable PHP files outside the active theme, resulting in conditional Remote Code Execution (RCE).

    Source: GitHub Security / Researcher PoC Repository

Vulnerability Details — CVE-2026-87902

An unauthenticated attacker can make get_page_template() page-template resolution include a chosen readable local .php file outside the active theme directories. If relevant pre-conditions for both the server and the active theme are met, this can lead to RCE.

Source

Public query vars pagename and page_id, accepted unauthenticated from GET or POST (WP::parse_request(); POST preferred so the value is not rewritten by canonical redirect). page_id must resolve to a published Page so is_page is true and the 404 template does not shadow the chain. Taint is read later via get_query_var('pagename') in wp-includes/template.php. Early sanitizers (wp_basename(), sanitize_title_for_query() / sanitize_title_with_dashes()) leave valid %xx octets intact — %2f is not treated as a path separator.

Payload

Double-encoded traversal in pagename (wire form %252e%252e%252f / mixed-case hex). PHP/the SAPI decodes once to %2e%2e%2f; get_page_template()'s extra urldecode() then yields ../. The candidate is always page-{decoded}.php, so the first path segment must complete a real top-level theme directory whose name starts with page- (typical: templates → page-templates/). Remaining ../ segments (depth ~1–12) walk to any readable .php; WordPress appends .php. The custom-template slug from post meta is validate_file()-gated; this pagename candidate is not.

Sink

get_page_template() pushes "page-{$pagename_decoded}.php" into the hierarchy with no validate_file(). get_query_template() → locate_template() concatenates that string onto the active theme directory and accepts the first file_exists() hit — no jail to stylesheet/template roots. template-loader.php then includes the resolved path (CWE-98). RCE is conditional: a reachable argument-taking PHP (e.g. pearcmd.php) plus register_argc_argv=On, so +-prefixed query tokens become $argv in the included file.

First, it updates the check in get_page_template() so the decoded name is added only if 0 === validate_file( $pagename_decoded ). Second, it adds _wp_is_template_path_allowed() to locate_template(). For names that contain traversal, this function resolves the full path and compares it with the active theme, the parent theme, and the compatibility directories. A path that points to wp-content/index.php is outside these directories, so the check rejects it. Technical breakdown

Technical breakdown

The first weak point is in get_page_template(). The following excerpt from vulnerable wp-includes/template.php shows the branch that prioritizes a decoded page name:

PHP
$pagename_decoded = urldecode( $pagename );
if ( $pagename_decoded !== $pagename ) {
    $templates[] = "page-{$pagename_decoded}.php";
}

There is no traversal check on $pagename_decoded. The generated name goes to get_query_template(), which calls locate_template(). In the vulnerable locator, an existing file is enough to select a candidate:

PHP
if ( file_exists( $wp_stylesheet_path . '/' . $template_name ) ) {
    $located = $wp_stylesheet_path . '/' . $template_name;
    break;
}

The concatenation does not enforce a directory boundary. If $template_name contains ../, file_exists() can succeed for a PHP file outside $wp_stylesheet_path; the selected path is then included by the template loader. The excerpts are from WordPress's get_page_template() and locate_template() source; the upstream fix changes both paths.

For example, our lab sends a page request whose pagename contains double-encoded slashes and dots:

HTTP
GET /?page_id=2&pagename=templates%252F%252E%252E%252F%252E%252E%252F%252E%252E%252F…

The decoding and file selection happen in stages:

  1. PHP decodes the query string once. WordPress receives templates%2F%2E%2E%2F%2E%2E%2F%2E%2E%2Findex as the pagename value. The encoded dots survive WordPress's page-name sanitization; literal .. did not survive in our lab.
  2. page_id=2 selects a real published page, so the request reaches the page-template hierarchy. A pagename request on its own returned 404 in our setup.
  3. get_page_template() runs urldecode() and constructs page-templates/../../../index.php from the decoded value.
  4. With a page-templates directory in the active theme, locate_template() finds that path. In our lab, /wp-content/themes/cve-lab/page-templates/../../../index.php resolves to /wp-content/index.php.
  5. The template loader includes the resolved PHP file. The stock wp-content/index.php contains only a comment, so it produces an empty response body.

The fix changes the first check to require 0 === validate_file( $pagename_decoded ) before adding the decoded candidate. It also adds _wp_is_template_path_allowed() to locate_template(). For candidates with traversal, that function compares their resolved paths with the active theme, parent theme, and compatibility directories. A path into wp-content/index.php fails that check.
